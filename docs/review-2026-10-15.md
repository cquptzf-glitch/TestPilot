### F02 · P1 · 缺少 verify 的断言会直接通过，审核门禁也不拒绝

### F06 · P1 · 本机 RPC 无鉴权和 Origin 限制，审核与执行接口可被直接调用

### F07 · P1 · 两个 RPC 线程池并发共用同一 SQLite 连接，事务边界不安全

证据：[rpc.py:52](D:/MyCode/TestPilot/testpilot/rpc.py:52)、[rpc.py:630](D:/MyCode/TestPilot/testpilot/rpc.py:630)、[db.py:181](D:/MyCode/TestPilot/testpilot/storage/db.py:181)。

rpc-io 与 rpc-run 各有一个线程，但均操作 self._orch.conn。check_same_thread=False 只解除线程检查；WAL 和 busy_timeout 不能隔离同一个连接上的事务。一个请求的 commit 可以提交另一个请求尚未完成的事务。

验证：用同一内存连接模拟两个线程的 SQL 交错，IO 路径 commit 后，即使 run 路径抛异常回滚，两条写入都仍存在。该探针证明事务边界问题，未将全软件并发压力测试等同于已完成。

建议：每个执行上下文使用独立连接、显式事务和统一仓储边界；或串行化完整事务，避免只锁单条 SQL。不要以禁用运行期间所有查询来解决可观测性问题。

### F17 · P2 · 健康检查连续失败分支重复锁定同一互斥锁

证据：[engine.rs:366](D:/MyCode/TestPilot/testpilot/app/desktop/src-tauri/src/engine.rs:366)、[engine.rs:239](D:/MyCode/TestPilot/testpilot/app/desktop/src-tauri/src/engine.rs:239)。

触发：sidecar 状态仍 running、RPC 连续失败进入第 3 次失败分支。当前 7 项 Rust 测试没有覆盖此路径。本项为静态确认，未主动破坏用户的真实壳进程复现。

建议：用一个词法作用域读取 pid/restarts 的拷贝并释放锁，再调用 set_status；增加有截止时间的健康故障路径测试。

run/case 开始即落 running；壳手动重启直接杀进程，自动重启同样会启动新引擎，但启动建库/迁移没有将失去执行者的记录改为 interrupted/error。旧记录会长期显示执行中，污染看板与历史统计。

### F19 · P2 · 查看历史 run 时，默认基线可能选到之后的新 run

证据：[RunDetailPage.tsx:102](D:/MyCode/TestPilot/testpilot/app/desktop/src/pages/RunDetailPage.tsx:102)。

## 5. 设计缺陷与产品不足

### D1 · 用例、场景和复跑之间缺少确定的环境隔离

任务前置条件汇总后在 run 开始顺序 load_scene；多个用例各需不同场景时，最后加载的场景会覆盖前面的。进入每条用例、整例复跑前均没有统一 reset/setup/teardown；case_ctx 的 scene 是可选补充。场景加载失败只记录警告，仍继续执行，可能在错误环境下给出 pass。

证据：[orchestrator.py:551](D:/MyCode/TestPilot/testpilot/engine/orchestrator.py:551)、[orchestrator.py:302](D:/MyCode/TestPilot/testpilot/engine/orchestrator.py:302)、[executor.py:161](D:/MyCode/TestPilot/testpilot/engine/executor.py:161)。

建议：明确任务级、用例级、尝试级前置条件；前置失败标 blocked，跳过依赖步骤；每次复跑恢复同一初态，并记录人工干预与设备状态来源。

### D2 · 环境矩阵与稳定性混合了不同实验条件

env_compat 主键是“被测版本 + suite_id”（无方案时为用例集摘要），不包含 DSL 版本、方案成员版本、驱动模式、模拟器版本、复跑策略。后续写入还会用当前 driver_mode 覆盖元信息，但累积计数仍包含旧模式。稳定性按 case_id 汇总最近窗口，不区分产品版本和 DSL 版本，正常版本变更也可能被解释为偶发抖动。

验证：同产品版本/方案先 uia_only 失败，再 vision_only 通过，矩阵显示 pass=1/fail=1、driver_mode=vision_only。

证据：[service.py:440](D:/MyCode/TestPilot/testpilot/knowledge/service.py:440)、[stats.py:112](D:/MyCode/TestPilot/testpilot/engine/stats.py:112)。

建议：持久化实验条件指纹，默认在可比条件内统计；跨条件比较明确标注，避免把累计成功率当成兼容性结论。

### D3 · 失败签名过粗，已知问题可能吞掉新的失败

签名仅包含 error_type/action/target_key/page_key；page_key 没有生产代码维护，通常固定 main。device.call 没有 target，命令不同也会生成相同精确签名；assert.state 的不同路径/期望值也未进入签名。

验证：load_scene 与 inject_error 两种 device.call 失败得到同一摘要 1537f4850d8a。

证据：[signature.py:25](D:/MyCode/TestPilot/testpilot/knowledge/signature.py:25)、[executor.py:610](D:/MyCode/TestPilot/testpilot/engine/executor.py:610)。

建议：加入规范化的设备命令、错误码、断言路径/期望指纹及页面信息；保留错误族用于模糊召回，自动 block/retry 使用更严格的精确匹配。

### D4 · 归因先验过强，人审只能改处置，不能纠正根因

所有 verify_failed 默认归为 timing（0.5），规则一旦返回就不进入 LLM；大量真实业务断言失败因此只会产生时序建议。KBReview 允许改 disposition，但没有根因类别、证据和建议的修订接口，确认后难以建立正确的知识。

证据：[judge.py:105](D:/MyCode/TestPilot/testpilot/engine/judge.py:105)、[service.py:303](D:/MyCode/TestPilot/testpilot/knowledge/service.py:303)。

建议：低置信规则作为候选提示，允许进一步分析；提供人审修订根因和证据的结构化接口，并记录修订者、时间与旧值。

### D5 · 轨迹写失败与配置写失败缺少完整性和原子性保障

步骤轨迹写失败被吞为日志，run 仍可 completed/pass，没有 evidence_incomplete 指标。设置覆盖层直接 write_text，中途退出可能损坏配置。归档只导出 JSON，不打包截图/报告/模板等引用资源，且查询范围可包含尚在运行的记录，尚不能视作可独立恢复的证据归档。

证据：[recorder.py:109](D:/MyCode/TestPilot/testpilot/storage/recorder.py:109)、[service.py:441](D:/MyCode/TestPilot/testpilot/config/service.py:441)、[repos.py:374](D:/MyCode/TestPilot/testpilot/storage/repos.py:374)。

建议：执行状态与证据完整性分别报告；配置采用临时文件加原子替换和校验；归档仅选择已结束 run，包含资源清单/hash 与恢复校验。

### D6 · UI 和验收门禁偏重“存在/编译成功”

目前前端 package.json 无行为测试命令；跨语言契约测试能检查方法名/资源字符串，但不能发现中止按钮被禁用、未保存审核、复跑差异串轮、历史基线倒置等行为。Rust 7 项测试主要覆盖配置解析和日志格式。缺少真实闭环的验收证据，且设计文档与实现大量同步改写，容易失去独立验收标准。

建议：建立“原始需求 → 行为验收场景 → 实现入口 → 自动测试 → 实机证据”的矩阵；新增高价值的用户流程测试与故障注入，优先覆盖本报告问题，避免单纯增加数量。
