# 2026-10-23 全面代码逻辑 / 处理流程 / UI 操作流复审

> 目标：在不削弱 TestPilot 已有能力的前提下，减少重复解析、重复建任务、无效 RPC、平级按钮和页面跳转，让日常回归形成一条清晰主路径；高级能力保留但降级到二级入口。

## 1. 最终信息架构

### 1.1 日常回归主路径

```text
开始测试
  -> 选择用例
  -> 仅对“确实需要”的用例生成 / 更新 DSL
  -> 内嵌逐条审核（通过后自动下一条）
  -> 执行前确认
  -> 开始执行
  -> 执行与结果
```

普通使用者不再需要先理解“测试方案 / 测试任务”的区别，也不需要为了跑一次回归先手工创建方案和任务。

### 1.2 用例维护路径

```text
用例维护
  -> 拉取 / 增量同步 / SVN 变更生成
  -> 生成或更新 DSL
  -> 审核与编辑
```

同步、全量校准、SVN Agent 等能力仍保留，但不与日常执行入口竞争。

### 1.3 高级复用路径

```text
执行与结果
  -> 测试任务
  -> 测试方案
```

测试方案定位为“长期复用的固定用例集 + 默认参数”，测试任务定位为“可重复执行的快照”。两者都不是日常回归的前置条件。

## 2. 代码逻辑复审与修复

### 2.1 避免无意义 LLM 重解析

旧逻辑在“开始测试”中只要填写被测窗口 / 程序路径，就会把所选用例全部重新送进解析流程，即使某些用例已经 active、DSL 已审核且窗口完整。

现在只重解析：

1. 本身没有有效 DSL / 远端有更新的用例；
2. 确实缺被测窗口，并且本次提供了 appTarget 的用例。

已审核且目标完整的用例直接复用，减少 LLM 调用、等待时间和二次审核风险。

### 2.2 任务复用 fingerprint 修正

`caseRetry` 只影响一次 `task.run`，不改变任务快照本身。

旧 fingerprint 把 `caseRetry` 纳入，导致“0 次复跑 -> 1 次复跑”也重新创建任务。现改为只由：

- 用例 ID + DSL version；
- remote；
- driver mode；

决定任务是否可复用。

### 2.3 任务配置优先级明确

统一为：

```text
全局默认 < 测试方案默认 < 本次任务显式覆盖
```

并修复旧实现中“方案默认反向覆盖本次任务选择”的问题。

同时：

- `suite_id` 与 `case_ids` 禁止同时指定；
- case ID 按输入顺序去重；
- suite case ID 按顺序去重；
- 显式 `preconditions=[]` 不再被自动重新推导；
- task driver override 进入编排前校验合法值。

### 2.4 Task UI 与后端语义一致

任务页现在：

- “测试方案”和“临时用例”互斥；
- 驱动模式新增“使用方案 / 全局默认”；
- 显式选择 `auto` 就真的覆盖为 auto；
- “同步到禅道”始终显式传 true / false，不再因为参数省略而被全局默认反向开启。

避免“UI 看起来关闭，后端其实开启”的隐式行为。

### 2.5 禅道同步口径一致

`CaseService.sync()` 现在把最终解析出的 product ID 同时用于：

- 远端查询；
- watermark scope；
- source_sync_state。

`parse=true` 且没有待解析用例时，也返回稳定的批处理结构，而不是从对象结构退化成空字典。

### 2.6 Run 执行参数早校验

RPC 在进入执行器前校验：

- driver mode；
- caseRetry 0..3。

错误直接返回 INVALID_PARAMS，不再让非法参数深入执行链后才失败。

### 2.7 停止执行竞争窗口修复

顶部“停止执行”现在消费 `task.abort` 返回的 `stopping`：

- stopping=true：保持停止中状态；
- stopping=false：说明 run 可能在点击瞬间已经结束，立即回读 run.list 并重新同步顶部状态。

避免界面永久停在“正在停止…”。

### 2.8 Run progress 事件契约修复

这是本轮发现的关键流程缺陷。

旧事件实际形态：

```json
{
  "run_id": 12,
  "stats": {
    "phase": "finished"
  }
}
```

但桌面端一直读取 `payload.phase`，因此 start / finished 事件无法按设计被前端识别，只能被轮询间接纠正。

现在事件统一为：

```json
{
  "run_id": 12,
  "phase": "finished",
  "stats": {}
}
```

因此：

- 顶部执行条；
- Runs 自动刷新；
- Tasks 自动刷新；
- RunDetail 收尾刷新；

都真正按事件驱动工作。

### 2.9 Router 学习统计重复计数修复

旧执行链：

```text
定位成功 -> router success +1
动作失败 -> router fail +1
```

一次真实 driver attempt 被统计成两次样本。

现在一次尝试只写一次最终结果：

- 定位失败 = fail；
- 定位成功 + 动作失败 = fail；
- 定位成功 + 动作成功 = success。

`avg_locate_ms` 仍保持定位耗时口径，不混入动作耗时。

### 2.10 capability-aware fallback

旧逻辑会在“驱动能定位、但不支持动作”时过早失败，例如：

```text
vision_first + ui.select
vision 定位成功
vision 不支持 select
=> action_failed
=> 因担心副作用，不再尝试 UIA
```

但“能力缺失”发生在动作前，没有副作用风险。

现改为动作前 capability preflight：

- 不支持该动作的驱动直接跳过；
- 后续支持该动作的驱动继续尝试；
- 只有真正执行动作后失败，才保持“不自动换驱动”的副作用保护；
- 所有驱动都不支持时返回 `capability_missing`。

同样修复了 `ui.wait state=gone` 在 `vision_first` 下被 Vision 的能力缺失提前击穿、无法落到 UIA 的问题。

### 2.11 DSL 动作白名单单一来源

复审 CI 时发现：`core.dsl` 已经支持 `ui.right_click / ui.scroll / ui.drag`，
Prompt 也会引导模型生成这些动作，但 `llm_gateway` 仍保存一份旧版
`KNOWN_ACTIONS` 副本。

这会造成：

- DSL 层认可；
- Prompt 层生成；
- LLM 归一化层却把它标成 uncertain。

现在 `llm_gateway` 直接复用 `core.dsl.KNOWN_ACTIONS`，动作表只保留一个权威来源。
对应测试按动作构造合法最小参数，避免 scroll / drag 因测试输入本身非法产生误报。

### 2.12 内嵌 DSL 审核队列使用最新状态推进

Workflow 之前在 `dsl.accept` 后调用异步 `cases.reload()`，然后立即基于旧
`chosen` 快照寻找下一条待审核用例。

在 reload 尚未完成的竞争窗口中，旧快照可能再次包含刚刚已经通过的用例，导致
“自动下一条”跳回旧项。

现在每次 accept 后：

1. 直接回读最新 `case.list`；
2. 只在本次 selection 中寻找仍未 approved 的下一条；
3. 无待审核项时进入执行阶段；
4. 后台再刷新页面缓存。

因此批量审核不再依赖 React 异步刷新时序。

## 3. UI / UX 复审与简化

### 3.1 主导航从“功能清单”改成“用户目标”

主导航收敛为 6 项：

1. 开始测试
2. 自动化探索
3. 用例维护
4. 执行与结果
5. 问题与知识
6. 设置

“测试任务 / 测试方案”进入“执行与结果”的二级 Tab。

### 3.2 用例维护页去工具箱化

默认只保留：

- 开始测试；
- 生成 / 更新 DSL；
- 审核 DSL。

以下能力降为二级：

- 拉取指定禅道用例；
- 增量同步；
- 全量校准；
- 生成全部待更新；
- 创建独立任务；
- 保存测试方案。

行尾动作也从多个按钮压缩为单一上下文动作。

### 3.3 开始测试页渐进式披露

执行前默认只展示：

- 用例数；
- 总步骤；
- 当前驱动模式摘要；
- 失败复跑摘要；
- 开始执行。

驱动方式、失败复跑、禅道同步收进“执行选项”。

被测软件设置在缺窗口信息时自动展开，否则保持次要。

### 3.4 DSL 批量审核减少一次点击

队列审核中：

```text
保存并通过 -> 自动进入下一条
```

嵌入“开始测试”的审核队列在最后一条完成后自动进入执行前确认；独立审核页则在整批真实完成后直接带原选择进入“开始测试”。

### 3.5 SVN 变更生成改成单主动作

旧页面同时摊开“配置 / 快照 / Agent 结果”三块空区域。

现在：

- 顶部配置范围；
- 主按钮“分析变更并生成测试用例”；
- “仅预览修改”为次操作；
- 有快照才展示快照；
- 有结果才展示结果。

### 3.6 Settings 主操作改为保存并重启

日常配置：

```text
修改 -> 保存并重启
```

“仅保存”保留给需要连续修改多个 Tab 的场景。

### 3.7 自动化探索按频率分层

UIA 第一层：

- 点击；
- 输入；
- 选择；
- 读取；
- 断言文本。

高级区：

- right click；
- SetValue + 回读；
- toggle；
- keypress；
- scroll；
- drag；
- screenshot diff。

Vision 同样把模板、稳定 key、region、diff、手势动作降为高级区。

会话的新建 / 关闭 / 清空也收进“会话管理”。

### 3.8 Run 结果页改成 result-first

默认概览只突出：

- 通过 / 失败 / 阻塞 / 跳过；
- 与基线上一次 run 的变化；
- 失败原因；
- 抖动 / 复跑 / KB 命中提示。

驱动统计、环境、LLM、env_compat 统一进入折叠的“技术诊断”。

同时修掉一个误导项：旧“最慢步骤 TOP”实际只统计当前默认选中的单个 case，却在 run 概览里表现成全 run 统计，因此删除。

### 3.9 诊断数据按需加载

以下 RPC 不再进入 RunDetail 就立即请求：

- `run.stepTrace`：只有进入轨迹 Tab 才加载；
- `kb.caseCtxList`：只有轨迹 Tab 才加载；
- `kb.envCompat`：只有打开技术诊断才加载。

减少页面初次打开的无效计算和数据库查询。

### 3.10 后台 job 面板降低常驻成本

旧 CaseJobsPanel 无论是否有任务，都每秒请求一次 `job.status`，并且完成结果会长期占据页面。

现在：

- active job：1 秒轮询；
- idle / terminal：5 秒低频巡检；
- 本前端启动 job 时通过事件立即刷新；
- 完成 / 失败结果支持手动关闭。

### 3.11 高频交互再收敛

后续实际复审继续做了三处小改动，不增加后端复杂度：

1. Workflow 的审核用例标签改为可点击，用户可以直接跳到任意待审核用例，也可以回看已确认用例，不再只能依赖“自动下一条”；
2. Cases 页删除与顶部快捷 chip 重复的“同步状态”下拉，减少一套重复筛选入口；“清除筛选”同时清理分组条件；
3. 后台任务完成后只保留一个明确主动作：有 DSL 结果时“继续审核”，否则有生成用例时“查看生成用例”；技术轨迹统一留在“查看详情”。

该增量只改 Desktop 交互，不新增 RPC、数据库字段或后端流程。

### 3.12 探索与失败回看继续减噪

继续复审 Automation / RunDetail 后，只做四处轻量调整：

1. “视觉断言”只在 Vision 模式显示，不再混入 UIA 操作区；
2. 清空探索会话复用统一 `ConfirmBar` 做二次确认，并在没有历史步骤时禁用清空按钮；
3. Run 概览若存在 fail / blocked，用一个主按钮直接进入第一条问题用例的轨迹回放；
4. Run 概览不再重复显示顶部 PassBar；切到用例明细 / 轨迹回放时仍保留顶部结果摘要。

这些修改全部复用已有状态与跳转函数，没有新增 RPC、数据库字段或执行逻辑。

### 3.13 探索固化改为单主动作

探索完成后的旧主路径需要：

```text
生成草稿 -> 保存并进入审核
```

其中草稿还是一个可过期的中间状态：预览后如果修改用例 ID / 标题，或继续调整探索历史，再保存时容易让界面当前状态与实际导入草稿产生认知偏差。

现在默认主路径改为：

```text
固化并进入审核
```

该动作会始终按**当前探索历史 + 当前用例 ID + 当前标题**重新生成 DSL、校验可固化步骤和 active case 冲突，然后导入并直接进入审核。

“预览 DSL 草稿”保留为次操作，仅用于查看；修改用例 ID / 标题会立即清掉旧预览。最终固化不依赖预览草稿，因此不存在把过期预览直接导入的问题。

本次仍只修改 Desktop 页面，复用现有 `automation.draft / case.list / case.import` RPC，没有新增接口或数据结构。

### 3.14 独立审核完成后直接继续测试

独立 DSL 审核页过去在队列最后一条通过后只提示“本批用例已全部审核完成”，用户还需要手动回到“开始测试”，并重新进入同一批用例。

同时旧判断还有一个边界：它按“当前是否位于队列最后一项”判断整批完成。用户如果手动先跳到最后一条，前面仍有待审用例时也可能收到错误的完成提示。

现在每次 `dsl.accept` 成功后：

1. 回读最新 `case.list`；
2. 对本次 queue / 单用例使用共享 `caseIsApproved` 语义重新计算真正待审项；
3. 仍有待审项时跳到第一条真实待审用例，不依赖当前位置；
4. 全部通过时直接 `navigate('home', { selection, ready: 1 })`，把原用例范围交给 Workflow；
5. 主按钮在当前确认会完成整批时显示“保存并通过，开始测试 →”。

Workflow 已支持 `selection` 参数，会直接复用这批用例，因此没有新增跨页持久状态、RPC 或数据库结构。嵌入 Workflow 的审核逻辑保持原样：全部确认后直接进入执行前确认。

### 3.15 审核完成直达执行前确认

继续检查“审核 → 执行”后发现，独立审核虽然已经能把原 selection 带回“开始测试”，但 Workflow 仍从第 1 步“选择用例”打开。对于刚刚完成整批审核的用例，这会形成一个纯重复点击：

```text
审核全部通过
  -> 回到已选好的用例列表
  -> 再点“下一步：执行测试”
  -> 执行前确认
```

现在独立审核完成后增加轻量 `ready=1` 路由提示：

```text
审核全部通过
  -> 执行前确认
  -> 用户明确点击“开始执行”
```

这里**没有自动执行测试**。真实 UI 自动化会操作桌面，因此“开始执行”仍保留为唯一必须的人为确认。

同时补了两层保护：

1. `ready=1` 必须同时带显式 `selection`，不会拿 sessionStorage 中的旧选择静默跳到执行前确认；
2. Workflow 加载最新用例后重新检查 `runnable` 和被测窗口信息；状态已变化、仍有未审核用例或缺窗口时，自动退回“选择用例”处理必要条件。

嵌入 Workflow 的审核正常成功时已经会自动进入 phase 3，因此移除原先常驻的重复“全部已确认，前往执行”主动作；仅在刷新/状态推进异常、页面仍留在审核阶段但实际已经全部可执行时，显示“已全部确认，继续执行”作为恢复入口。

本次只修改 Desktop 路由与页面状态，不新增 RPC、数据库字段或执行器逻辑。

### 3.16 执行失败优先恢复已有 run，避免误重试

继续审查“开始执行”异常路径后确认，`task.run` 的失败不能简单等同于“测试没有执行”：

- run 尚未创建前的前置错误会直接返回异常；
- begin_run 之后的致命异常会把 run 收尾为 `error` 并保留现场；
- 协作中止正常返回 `aborted`；
- RPC 连接中断时，后端 run 可能仍在 running，甚至已经 completed。

旧 Workflow 只显示一条错误文本，任务虽然会保留以便重试，但在“RPC 调用失败、实际 run 已经产生”的情况下直接重试可能造成一次不必要的重复执行。

现在执行前先读取该任务最近一次 run ID，仅作为恢复基线；这个查询失败**不会阻塞测试执行**。当 `task.run` 调用失败时：

1. 不解析错误字符串、不按文案猜故障类型；
2. 只有执行前最近 run 已成功读取时，才再次查询该任务最新 run；
3. 如果出现新的 run，不论其当前状态是 running / completed / error / aborted，都优先显示“查看本次运行”，不提供直接重试；
4. 确认没有新 run 时，保留已创建的本地任务并显示“重试已有任务”，避免重复建任务；
5. 同时保留“返回修改范围”，用于调整用例范围或重新处理必要配置；
6. 用例范围、驱动模式、remote、复跑次数或流程阶段发生变化时，旧执行错误提示自动失效，避免陈旧恢复动作残留。

因此异常恢复原则变成：

```text
RPC / 启动异常
  -> 先确认是否已经产生本次 run
     -> 有：查看这个 run
     -> 无：复用已有 task 重试
```

这次仍只改 Desktop Workflow，没有新增 RPC、数据库字段或后端错误分类表；恢复依据来自已有 `run.list(taskId)` 的事实状态，而不是脆弱的字符串匹配。

## 4. 不做的简化

本轮不是“删功能”，以下能力保留：

- 测试方案；
- 独立测试任务；
- 禅道远端任务；
- 全量校准；
- Vision / UIA / Device 高级动作；
- run 环境、驱动、LLM 诊断；
- DSL JSON 级编辑；
- KB / env_compat。

原则是：**默认路径只呈现当前决策所需信息，高级能力按需展开。**

## 6. 回归测试新增重点

本轮新增 / 调整测试用于固定：

- task override 优先级；
- suite / direct case scope 互斥；
- case ID 去重；
- 非法 task driver mode；
- 非法 run mode / caseRetry；
- Zentao effective product scope；
- 空 parse batch 返回结构；
- router action failure 只记一次样本；
- wait_gone capability fallback；
- 通用 UI action capability fallback；
- clear-input capability fallback；
- run.progress 的 phase 顶层事件契约。
